34. MEMORY PROMPTING
=====================================================================
Part of: The Ultimate Prompt Engineering Library (Part 1: Knowledge)
Author: Deb Barman
=====================================================================

-----------------------------
1. TITLE
-----------------------------
Memory Prompting — Maintaining Context and Continuity Across 
Interactions

-----------------------------
2. DEFINITION
-----------------------------
Memory prompting is a technique for explicitly managing what 
information a model RETAINS, RECALLS, or FORGETS across multiple 
turns of a conversation or across genuinely separate sessions — since 
LLMs do not inherently "remember" anything beyond what's included in 
their current context window. This involves designing prompts and 
system architecture that deliberately store important information 
(user preferences, prior decisions, established facts), retrieve the 
right memories at the right time, and organize different TYPES of 
memory (short-term working memory, long-term persistent facts, 
episodic history of past interactions) — directly relevant to complex 
memory-layer architectures like Deb Barman's Godfather Agent system 
with its 7 distinct memory layers.

Think of it like the difference between a conversation with a stranger 
who forgets everything the moment you stop talking (a model with no 
memory management) versus a conversation with a close colleague who 
remembers your past discussions, your stated preferences, and 
important decisions you made together weeks ago (a model with 
well-designed memory prompting/architecture) — even though, 
technically, neither the stranger nor the colleague's brain works 
identically to how you're storing and retrieving information for the 
model.

-----------------------------
3. PURPOSE
-----------------------------
Memory prompting exists to:
- Provide CONTINUITY across long conversations or multiple separate 
  sessions, so the model doesn't need everything re-explained from 
  scratch every single time.
- Enable PERSONALIZATION — remembering a specific user's preferences, 
  history, and context to provide more relevant, tailored responses 
  over time.
- Support long-running AGENTIC systems that need to track state, 
  progress, and prior decisions across many steps or an extended 
  period of operation.
- Manage the fundamental LIMITATION that LLMs have no built-in 
  persistent memory — everything must be explicitly stored somewhere 
  (a database, a summary, a vector store) and explicitly re-injected 
  into context when relevant.
- Organize DIFFERENT TYPES of memory appropriately (e.g., short-term 
  working context vs. long-term persistent facts vs. episodic history 
  of past events) since different types of information benefit from 
  different storage/retrieval strategies.

-----------------------------
4. WHEN TO USE AND BEST MODEL OR LLM
-----------------------------
WHEN TO USE:
- Building any application requiring CONTINUITY across multiple 
  sessions (chatbots that remember users, personal assistants, 
  long-running agents).
- Conversations/tasks that exceed a single context window's capacity, 
  requiring some form of summarization or selective memory retention.
- Multi-agent systems where different agents need to share certain 
  persistent state/knowledge (relevant to swarm architectures with 
  dedicated memory layers).
- Personalization features where remembering user-specific 
  preferences/history genuinely improves the user experience.
- Long-running autonomous agent tasks that need to track progress and 
  prior decisions over an extended operation period.

WHEN NOT TO USE:
- Simple, single-turn, stateless tasks where no continuity is needed 
  at all.
- Situations where persisting information raises genuine privacy 
  concerns that outweigh the personalization benefit — always consider 
  data privacy/consent implications when designing memory systems.
- When the "memory" need is small enough to simply fit within a single 
  conversation's context window without requiring any external 
  storage/retrieval architecture.

BEST MODELS FOR MEMORY-BASED SYSTEMS:
- Claude (with large context windows, 200K+) — excellent for holding 
  substantial conversation history directly in context without 
  external memory infrastructure for moderately long interactions.
- GPT-4o/4.1/5-class — strong performance combined with memory-
  management frameworks/APIs for longer-term persistence needs.
- Gemini 1.5/2.x Pro (1M-2M token context) — exceptional for 
  applications that can simply keep MORE raw history directly in 
  context rather than needing aggressive summarization, due to the 
  massive context window.
- For TRUE PERSISTENT memory across sessions (beyond a single context 
  window), you need external infrastructure regardless of model 
  choice: vector databases (ChromaDB, FAISS, Pinecone) for semantic 
  memory retrieval, traditional databases for structured fact storage, 
  and summarization pipelines for condensing conversation history — 
  the MODEL itself doesn't inherently persist anything between API 
  calls.
- Frameworks like LangGraph, Google ADK, and custom memory-layer 
  architectures (like Godfather Agent's 7-layer system) provide the 
  orchestration needed to properly manage multiple memory types.

-----------------------------
5. PROMPT FORMULA
-----------------------------
    [RETRIEVED/RELEVANT MEMORY] + "Based on what you know about 
    [PERSON/CONTEXT] from previous interactions: [MEMORY CONTENT], 
    respond to their current request: [CURRENT QUERY]"

-----------------------------
6. PROMPT STRUCTURE
-----------------------------
    1. Memory Retrieval/Injection — the relevant stored 
       facts/preferences/history retrieved from your memory system and 
       inserted into the current prompt's context.
    2. Memory Type Labeling (optional but useful) — distinguishing 
       different kinds of memory (e.g., "Established facts:", "User 
       preferences:", "Recent conversation summary:") for clarity.
    3. Current Query/Task — what the user/system is asking for right 
       now.
    4. Update Instruction (for systems that need to extract NEW 
       memory-worthy information) — ask the model to identify what new 
       information from this interaction should be stored for future 
       reference.

Example skeleton:
    "Established facts about this user/project: 
    [MEMORY ITEM 1] 
    [MEMORY ITEM 2] 
    
    Recent conversation summary: [CONDENSED SUMMARY OF EARLIER 
    DISCUSSION IF THE FULL HISTORY DOESN'T FIT IN CONTEXT] 
    
    Current request: [CURRENT USER QUERY] 
    
    Respond to the current request using the above context where 
    relevant. [OPTIONAL: Also identify any new information from this 
    exchange that should be added to memory for future reference.]"

-----------------------------
7. BEST PRACTICES
-----------------------------
- Distinguish between MEMORY TYPES explicitly — short-term/working 
  context (this immediate conversation), long-term/persistent facts 
  (stable preferences, established project details), and episodic 
  history (a log of past significant interactions) often benefit from 
  different storage and retrieval strategies.
- Only inject RELEVANT memory into the current context — dumping 
  every piece of stored memory into every prompt wastes context space 
  and can dilute focus; use retrieval (often semantic/vector-based) to 
  select only what's actually relevant to the current query.
- For long conversations exceeding context limits, use SUMMARIZATION 
  — periodically condense older parts of the conversation into a 
  compact summary rather than either dropping them entirely or trying 
  to keep everything verbatim forever.
- Build an explicit MEMORY UPDATE step — after significant 
  interactions, extract and store new memory-worthy facts, rather than 
  only ever reading from memory without ever writing new information 
  to it.
- Handle MEMORY CONFLICTS explicitly — what happens if newly stated 
  information contradicts something previously stored (e.g., a user's 
  preference changed)? Generally, prioritize more recent information 
  while noting the change.
- Consider PRIVACY and DATA RETENTION policies carefully when 
  designing persistent memory systems — be transparent about what's 
  stored and for how long, and provide mechanisms for users to view/
  delete their stored information.
- For multi-agent systems with SHARED memory, clearly define which 
  memory layers are agent-specific (private working memory) vs. 
  genuinely shared across the whole system (global facts all agents 
  should access).

-----------------------------
8. COMMON MISTAKES
-----------------------------
- MISTAKE: Injecting ALL stored memory into every prompt regardless of 
  relevance, wasting context space and diluting focus on the current 
  task.
  FIX: Use relevance-based retrieval to select only pertinent memory 
  items for the current context.

- MISTAKE: No memory update mechanism, meaning the system never 
  actually learns/stores new information from ongoing interactions.
  FIX: Build an explicit step to extract and persist new memory-worthy 
  facts after significant exchanges.

- MISTAKE: Not handling memory conflicts (e.g., contradictory 
  information stated at different times), leading to confusing or 
  inconsistent behavior.
  FIX: Explicitly prioritize more recent information while flagging 
  the change when a conflict is detected.

- MISTAKE: Trying to keep an entire long conversation history verbatim 
  in context indefinitely, eventually exceeding context limits or 
  degrading performance due to excessive length.
  FIX: Implement periodic summarization to condense older history into 
  compact form.

- MISTAKE: Ignoring privacy/data retention considerations when 
  designing systems that persist personal information across sessions.
  FIX: Design with transparency, user control, and appropriate data 
  handling policies from the start.

-----------------------------
9. EXAMPLES (BASIC, INTERMEDIATE, ADVANCED)
-----------------------------

--- BASIC EXAMPLE ---
Prompt:
"Established facts about this user: 
- Prefers concise, direct answers without lengthy preambles 
- Is learning Python as a beginner 

Current request: 'Explain what a for loop does.' 

Respond to the current request, keeping in mind the user's stated 
preferences above."

Expected Output:
A concise, direct explanation of for loops (no lengthy preamble), 
pitched appropriately for a beginner Python learner, actively 
reflecting both stored preference facts.

--- INTERMEDIATE EXAMPLE ---
Prompt:
"Established facts about this project: 
- The user is building a multi-agent AI system called 'Godfather 
Agent' using Google ADK and Gemini 2.0 Flash 
- The system has 7 memory layers: working, episodic, semantic, 
procedural, emotional, social, and meta-memory 
- Previous conversation established that the 'God Mode pipeline' 
allows top-level override of individual agent decisions 

Recent conversation summary: The user was previously troubleshooting 
high latency (4.2s per response) caused by every query triggering 
reads across all 7 memory layers even when unnecessary. 

Current request: 'I implemented the memory router you suggested last 
time — latency is down to 1.3 seconds. What should I focus on 
optimizing next?' 

Respond using the above context, and note any new information from 
this exchange that should be added to memory for future reference."

Expected Output:
A response that correctly references the prior latency issue and the 
suggested memory router solution, acknowledges the reported 
improvement (4.2s → 1.3s), and offers a relevant next optimization 
suggestion building on the established 7-layer architecture context 
— followed by an explicit note such as: "New information to store: 
memory router solution successfully implemented; latency improved 
from 4.2s to 1.3s as of this conversation."

--- ADVANCED EXAMPLE ---
Prompt:
"MEMORY SYSTEM CONTEXT (for an AI assistant with layered memory):

Long-term persistent facts: 
- User is a self-taught Python developer, Class XI student, based in 
  Siliguri, West Bengal 
- Deep technical stack: PyTorch, LangChain/LangGraph, Google ADK, 
  ChromaDB/FAISS, FastAPI 
- Core aesthetic preference: cyberpunk/dark themes across projects 

Episodic memory (relevant past interactions, semantically retrieved 
for this query): 
- [3 weeks ago] Discussed BLACKCORE cryptographic vault design using 
XChaCha20-Poly1305, Argon2id, and Shamir Secret Sharing 
- [1 week ago] Discussed adding ghost/honey vault modes for plausible 
deniability 

Working memory (this session so far): 
- User has been asking about semantic caching for a separate RAG 
project in this current conversation 

Current request: 'Going back to BLACKCORE for a second — should the 
honey vault mode use a completely separate encryption key from the 
real vault, or derive it from the same master key?' 

Respond using the relevant retrieved memory (note that this question 
relates to the EPISODIC memory about BLACKCORE, not the CURRENT 
session's RAG caching topic — correctly retrieve and prioritize the 
relevant memory layer rather than the most recent working memory). 
Also note what new information from this exchange should be added to 
episodic memory."

Expected Output:
A technically grounded response addressing the BLACKCORE honey-vault 
key derivation question specifically (correctly pulling from episodic 
memory about the cryptographic vault project rather than getting 
confused by the unrelated current-session RAG caching discussion), 
likely recommending a genuinely separate/independently-derived key 
for the honey vault rather than deriving it from the same master key 
(since a shared derivation could create a cryptographic link an 
attacker might exploit to infer the existence of the real vault, 
undermining the plausible deniability goal established in the prior 
conversation) — followed by an explicit memory update note such as: 
"New episodic memory to store: clarified that honey vault mode should 
use an independently-derived encryption key, separate from the real 
vault's master key, to preserve plausible deniability guarantees."

-----------------------------
10. REUSABLE PROMPT TEMPLATE
-----------------------------
    Long-term persistent facts: [STABLE, RARELY-CHANGING FACTS ABOUT 
    THE USER/PROJECT]
    
    Episodic memory (relevant past interactions): [SEMANTICALLY 
    RETRIEVED PAST EXCHANGES RELEVANT TO THE CURRENT QUERY]
    
    Working memory (this session): [SUMMARY OF THE CURRENT ONGOING 
    CONVERSATION, IF RELEVANT]
    
    Current request: [WHAT'S BEING ASKED RIGHT NOW]
    
    Respond to the current request, prioritizing the MOST RELEVANT 
    memory layer(s) for this specific query (not necessarily the most 
    recent). 
    
    [OPTIONAL: Note any new information from this exchange that 
    should be stored in memory for future reference.]
