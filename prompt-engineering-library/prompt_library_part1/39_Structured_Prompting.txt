39. STRUCTURED PROMPTING

Part of: The Ultimate Prompt Engineering Library (Part 1: Formatting)

-----------------------------
1. TITLE
-----------------------------
Structured Prompting — Using Explicit Formatting to Organize Prompts 
and Outputs

-----------------------------
2. DEFINITION
-----------------------------
Structured prompting is a technique where you use EXPLICIT FORMATTING 
elements — headers, numbered sections, XML-style tags, bullet lists, 
delimiters, tables — to organize BOTH your input prompt AND your 
requested output into clearly delineated, unambiguous sections. Rather 
than writing a single flowing paragraph and hoping the model correctly 
parses what's an instruction vs. what's input data vs. what's a 
constraint, structured prompting makes these boundaries explicit and 
visually/syntactically clear — dramatically improving the model's 
ability to correctly parse complex, multi-part prompts and produce 
consistently organized output.

Think of it like the difference between giving someone instructions as 
one long, run-on paragraph versus giving them a clearly formatted memo 
with distinct headers: "BACKGROUND:", "TASK:", "CONSTRAINTS:", 
"FORMAT:" — the SAME information is being conveyed, but the structured 
version is dramatically easier to parse correctly and reduces the 
chance of missing or misinterpreting any single part.

-----------------------------
3. PURPOSE
-----------------------------
Structured prompting exists to:
- Reduce AMBIGUITY about which part of a prompt is an instruction, 
  which is input data, and which is a constraint — explicit structure 
  removes guesswork.
- Improve PARSING ACCURACY for complex, multi-part prompts, especially 
  those combining several of the other techniques in this library 
  (e.g., a prompt with role + context + constraints + examples all 
  together).
- Produce more CONSISTENT, predictable output formatting across 
  multiple runs, since a structured request format naturally 
  encourages a structured response format.
- Support PROGRAMMATIC use cases where prompts are generated by code 
  (e.g., inserting variables into a template) and need reliable, 
  unambiguous boundaries between static instructions and dynamic 
  content.
- Serve as the FOUNDATIONAL formatting discipline that makes many 
  other advanced techniques (Few-Shot, RAG, Multi-Agent) work reliably 
  at scale, since those techniques depend on clearly distinguishing 
  different content types within a single prompt.

-----------------------------
4. WHEN TO USE AND BEST MODEL OR LLM
-----------------------------
WHEN TO USE:
- Any complex prompt combining MULTIPLE distinct elements (role, 
  context, task, constraints, examples) that could otherwise blur 
  together in flowing prose.
- Prompts that will be generated PROGRAMMATICALLY (via code, inserting 
  variables into a template) where reliable parsing boundaries matter.
- Situations where you've noticed the model MISSING or misinterpreting 
  part of a complex prompt written in plain flowing text.
- Any task requiring a specific, consistent OUTPUT structure across 
  many runs (reports, structured analyses, multi-section documents).
- Building production prompt templates that will be reused many times 
  with different variable inputs.

WHEN NOT TO USE:
- Very simple, single-part requests where formatting overhead adds 
  nothing (a quick, casual question doesn't need XML tags).
- Casual conversational exchanges where heavy structural formatting 
  would feel unnaturally rigid/robotic.
- Purely creative, free-flowing tasks where imposing rigid structure 
  might constrain natural creative expression unnecessarily.

BEST MODELS FOR STRUCTURED PROMPTING:
- Claude — particularly well-known for excellent performance with XML-
  style tags specifically (e.g., <instructions>, <context>, 
  <examples>) as a structuring mechanism; Anthropic's own documentation 
  specifically recommends this approach for complex prompts with 
  Claude models.
- GPT-4o/4.1/5-class — responds well to both Markdown-style headers 
  and XML-style tags for structuring complex prompts.
- Gemini Pro/Ultra — good structured prompt handling, particularly 
  responsive to clear Markdown-style section headers.
- DeepSeek / Qwen — capable of parsing structured prompts, especially 
  well-suited to structured formats for coding-related tasks.
- Mistral / Llama — benefit from structured formatting, especially 
  smaller variants which can struggle more with parsing complex, 
  unstructured, flowing-prose prompts compared to clearly delineated 
  ones.
- GENERAL RULE: virtually ALL modern instruction-tuned models respond 
  better to structured, clearly-delineated prompts than to equally 
  complex information presented as one dense, undifferentiated 
  paragraph.

-----------------------------
5. PROMPT FORMULA
-----------------------------
    <role>[ROLE]</role> 
    <context>[BACKGROUND INFO]</context> 
    <task>[WHAT TO DO]</task> 
    <constraints>[RULES/LIMITS]</constraints> 
    <output_format>[HOW TO STRUCTURE THE RESPONSE]</output_format>
    (or equivalent using Markdown headers: ## Role, ## Context, ## 
    Task, etc.)

-----------------------------
6. PROMPT STRUCTURE
-----------------------------
    1. Choose a Structuring Method — XML-style tags (<tag>content
       </tag>), Markdown headers (## Section Name), numbered sections, 
       or a hybrid — consistency within a single prompt matters more 
       than which specific method you choose.
    2. Delineate Distinct Content Types — clearly separate role/
       persona, background context, the actual task/instruction, 
       constraints, examples (if any), and desired output format into 
       their own distinct, labeled sections.
    3. Use Consistent Formatting Throughout — if you start with XML 
       tags, use them throughout; don't mix XML tags in one section 
       with Markdown headers in another within the same prompt.
    4. Specify Output Structure — if you need a specific output 
       format, describe that structure explicitly too (which sections/
       headers the RESPONSE should contain), not just the input.

Example skeleton (XML-style):
    "<role>You are a [ROLE].</role> 
    <context>[RELEVANT BACKGROUND]</context> 
    <task>[SPECIFIC INSTRUCTION]</task> 
    <constraints> 
    - [CONSTRAINT 1] 
    - [CONSTRAINT 2] 
    </constraints> 
    <output_format>[DESCRIBE DESIRED RESPONSE STRUCTURE]
    </output_format>"

Example skeleton (Markdown-style):
    "## Role 
    [ROLE] 
    
    ## Context 
    [BACKGROUND] 
    
    ## Task 
    [INSTRUCTION] 
    
    ## Constraints 
    - [CONSTRAINT 1] 
    - [CONSTRAINT 2] 
    
    ## Output Format 
    [DESIRED STRUCTURE]"

-----------------------------
7. BEST PRACTICES
-----------------------------
- Pick ONE structuring convention (XML tags OR Markdown headers) and 
  use it CONSISTENTLY throughout a single prompt — mixing conventions 
  within the same prompt can reduce clarity rather than improve it.
- For Claude specifically, XML-style tags are a particularly well-
  supported and recommended structuring method, given how the model 
  was trained to work with this format.
- Name your tags/headers DESCRIPTIVELY (<context>, <task>, 
  <constraints>) rather than generically (<section1>, <section2>), so 
  the semantic meaning of each part is clear from the label itself.
- For PROGRAMMATICALLY generated prompts (inserting variables into 
  templates), structured formatting is especially valuable since it 
  creates reliable, predictable boundaries between static template 
  text and dynamically inserted content.
- Structure your OUTPUT FORMAT REQUEST the same way you structure your 
  input — if you want a response with specific sections, explicitly 
  describe (or even provide a skeleton of) that desired output 
  structure.
- Don't over-structure trivially simple prompts — reserve this 
  technique for genuinely complex, multi-part prompts where the 
  organizational benefit clearly outweighs the added formatting 
  overhead.
- When combining structured prompting with other techniques (Few-Shot, 
  RAG), use the structural tags to clearly delineate WHERE examples or 
  retrieved context begin and end (e.g., <examples>...</examples>, 
  <retrieved_context>...</retrieved_context>).

-----------------------------
8. COMMON MISTAKES
-----------------------------
- MISTAKE: Mixing structuring conventions within the same prompt (some 
  sections in XML tags, others as Markdown headers, others as plain 
  prose), reducing overall clarity.
  FIX: Pick one consistent structuring method and apply it throughout 
  the entire prompt.

- MISTAKE: Using generic, non-descriptive section labels (<section1>, 
  <part_a>) instead of semantically meaningful ones.
  FIX: Use descriptive labels like <context>, <task>, <constraints> 
  that convey the actual content's purpose.

- MISTAKE: Over-structuring very simple, single-part prompts where the 
  formatting overhead adds no real benefit and feels unnecessarily 
  rigid.
  FIX: Reserve heavy structural formatting for genuinely complex, 
  multi-part prompts.

- MISTAKE: Structuring the INPUT prompt carefully but not specifying 
  any structure for the desired OUTPUT, missing an opportunity for 
  more consistent, organized responses.
  FIX: Describe (or sketch) your desired output structure explicitly, 
  not just your input.

- MISTAKE: Using structured formatting in a way that feels robotic or 
  unnatural for genuinely casual, conversational exchanges.
  FIX: Reserve structured prompting for complex/technical/production 
  use cases, not casual chat.

-----------------------------
9. EXAMPLES (BASIC, INTERMEDIATE, ADVANCED)
-----------------------------

--- BASIC EXAMPLE ---
Prompt:
"<task>Write a short product tagline.</task> 
<context>The product is a reusable coffee cup made from recycled 
materials.</context> 
<constraints> 
- Maximum 10 words 
- Should emphasize sustainability 
</constraints>"

Expected Output:
A concise, correctly-scoped tagline (10 words or fewer) that clearly 
emphasizes sustainability, correctly synthesizing all three clearly-
delineated sections of the structured prompt.

--- INTERMEDIATE EXAMPLE ---
Prompt:
"## Role 
You are a technical writer specializing in developer documentation. 

## Context 
This documentation is for a Python library that provides a simple 
wrapper around common file I/O operations, intended for beginner 
Python developers. 

## Task 
Write a 'Getting Started' section for this library's README. 

## Constraints 
- Include one basic code example 
- Keep the tone friendly and encouraging for beginners 
- Maximum 150 words 

## Output Format 
A single markdown section with a header '## Getting Started', 
followed by a brief intro paragraph, then a code block example."

Expected Output:
A correctly-formatted markdown section exactly matching the specified 
output format (header, intro paragraph, code block), written in an 
appropriately friendly/beginner-focused tone, within the 150-word 
constraint, and including exactly one code example as requested — 
demonstrating the model correctly parsed and satisfied every distinct 
structured section of the prompt.

--- ADVANCED EXAMPLE ---
Prompt:
"<role>You are a senior code reviewer specializing in Python security 
best practices.</role> 

<context> 
This is a function from a production authentication system for a 
multi-agent AI platform (similar in purpose to Deb Barman's Godfather 
Agent system). The codebase follows PEP 8 conventions and uses type 
hints throughout. 
</context> 

<code_to_review> 
def authenticate_agent(agent_id, api_key): 
    stored_key = database.get_key(agent_id) 
    if api_key == stored_key: 
        return True 
    return False 
</code_to_review> 

<task> 
Perform a security-focused code review of the provided function. 
</task> 

<constraints> 
- Focus ONLY on security issues, not style/formatting issues 
- For each issue found, rate severity as Critical/High/Medium/Low 
- Provide a specific code-level fix for each issue 
</constraints> 

<output_format> 
Respond using this exact structure: 
## Security Issues Found 
For each issue: 
### [Severity]: [Issue Title] 
- Description: [...] 
- Fix: [code snippet or specific change] 
</output_format>"

Expected Output:
A response that precisely follows the specified output_format 
structure, correctly identifying security issues ONLY (per the 
constraint excluding style feedback) — such as the non-constant-time 
string comparison (`==`) being vulnerable to timing attacks (likely 
rated High or Critical given the authentication context) and the 
plaintext API key comparison/storage implications (likely rated 
Critical) — each formatted under its own "### [Severity]: [Issue 
Title]" header with a Description and a specific Fix (e.g., using 
`hmac.compare_digest()` for constant-time comparison, and ensuring 
keys are hashed rather than compared in plaintext) — demonstrating 
that the heavily structured, multi-tag prompt was parsed correctly 
across role, context, code, task, constraints, AND the specific 
requested output format simultaneously.
