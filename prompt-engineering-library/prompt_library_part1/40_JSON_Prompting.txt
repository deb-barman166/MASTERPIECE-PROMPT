-----------------------------
1. TITLE
-----------------------------
JSON Prompting — Requesting and Enforcing Machine-Readable Output

-----------------------------
2. DEFINITION
-----------------------------
JSON prompting is a specific, high-precision form of Structured 
Prompting where you instruct the model to produce its output 
EXCLUSIVELY as valid JSON (JavaScript Object Notation) matching a 
specific, defined schema — rather than natural language prose. This 
is essential for any use case where the model's output needs to be 
directly consumed by CODE (parsed programmatically, inserted into a 
database, passed to another function/API) rather than read by a human, 
since JSON provides an unambiguous, machine-parseable data structure 
with clearly typed fields.

Think of it like the difference between asking a colleague to describe 
a person's contact information in a sentence ("John's email is 
john@example.com and his phone number is 555-1234") versus asking them 
to fill out a structured digital form with distinct, labeled fields: 
{"name": "John", "email": "john@example.com", "phone": "555-1234"} — 
the second version can be directly and reliably processed by software, 
while the first would require additional, potentially error-prone 
parsing logic to extract the same information.

-----------------------------
3. PURPOSE
-----------------------------
JSON prompting exists to:
- Enable RELIABLE PROGRAMMATIC CONSUMPTION of model outputs — JSON can 
  be directly parsed by virtually any programming language without 
  fragile natural-language-parsing logic.
- Enforce a specific, consistent DATA SCHEMA across many requests, 
  ensuring every response has the same fields in the same format, 
  critical for batch-processing or pipeline integration.
- Support direct integration with DATABASES, APIs, and other software 
  systems that expect structured data input.
- Reduce ambiguity in EXTRACTION tasks (pulling specific structured 
  information out of unstructured text) by defining exactly what 
  fields should be extracted and in what format.
- Serve as the standard OUTPUT format underlying Function Calling 
  (file 31) and many production AI application architectures where 
  model outputs feed directly into further automated processing.

-----------------------------
4. WHEN TO USE AND BEST MODEL OR LLM
-----------------------------
WHEN TO USE:
- Any output that will be consumed by CODE rather than read directly 
  by a human (feeding into a database, another API, a downstream 
  processing script).
- Data extraction tasks — pulling specific structured fields out of 
  unstructured text (extracting names/dates/amounts from documents, 
  parsing resumes, structuring survey responses).
- Classification tasks where you need a consistent, parseable label/
  confidence output format.
- Building automated pipelines or batch-processing systems that need 
  uniform data structure across potentially thousands of requests.
- Any scenario naturally requiring Function Calling (file 31), since 
  JSON is the underlying format for structured function call outputs.

WHEN NOT TO USE:
- Conversational responses meant to be read directly by a human — 
  forcing JSON output for a casual chat response is unnecessary and 
  produces an unnatural user experience.
- Creative writing, long-form explanations, or nuanced discussions 
  where natural prose is genuinely the better format for human 
  comprehension.
- Simple, one-off tasks where you're manually reading the output 
  yourself and don't need programmatic parsing.

BEST MODELS FOR JSON PROMPTING:
- Claude — strong native JSON output reliability, especially when 
  using Anthropic's structured output / tool-use features which can 
  enforce schema compliance more strictly than prompt instructions 
  alone.
- GPT-4o/4.1/5-class (especially with OpenAI's "JSON mode" or 
  structured outputs feature) — excellent, very reliable JSON 
  generation, with dedicated API features specifically designed to 
  GUARANTEE valid JSON output (a significant reliability improvement 
  over just prompting for JSON in plain text).
- Gemini Pro/Ultra (with native JSON output configuration) — strong 
  JSON reliability, particularly when using Google's structured output 
  API features.
- DeepSeek / Qwen — generally capable JSON output, especially strong 
  for coding-related structured data tasks.
- Mistral / Llama — capable of JSON output when explicitly instructed, 
  though smaller models are more prone to occasional formatting errors 
  (trailing commas, unescaped quotes, missing brackets) compared to 
  larger models or dedicated structured-output API features.
- CRITICAL BEST PRACTICE: whenever available, use your provider's 
  DEDICATED structured output / JSON mode API feature (not just 
  prompting for JSON in plain text) since these features use 
  additional constraints (like grammar-based generation) to GUARANTEE 
  schema-valid output, which is significantly more reliable than 
  relying on the model to correctly format JSON purely through natural 
  language instruction.

-----------------------------
5. PROMPT FORMULA
-----------------------------
    [TASK] + "Respond ONLY with valid JSON matching this exact 
    schema: [SCHEMA DEFINITION]. Do not include any text before or 
    after the JSON object."

-----------------------------
6. PROMPT STRUCTURE
-----------------------------
    1. Task Instruction — what information needs to be extracted/
       generated/classified.
    2. Schema Definition — the exact JSON structure expected, 
       including field names, data types, and any nested structures.
    3. Strict Output Instruction — an explicit instruction that the 
       ENTIRE response must be valid JSON only, with no additional 
       prose, explanation, or markdown code fences (unless your 
       specific parsing setup expects fences).
    4. Example (optional but highly recommended) — a sample of the 
       exact expected JSON output structure, functioning as a One-
       Shot or Few-Shot example specifically for the JSON format.
    5. Edge Case Handling — instructions for how to represent missing/
       unavailable/null data within the JSON schema (e.g., using 
       `null` rather than omitting the field or leaving it as an empty 
       string ambiguously).

Example skeleton:
    "[TASK]. 
    
    Respond ONLY with valid JSON matching this exact schema: 
    { 
      "field_name_1": "string", 
      "field_name_2": number, 
      "field_name_3": boolean, 
      "field_name_4": ["array", "of", "strings"] 
    } 
    
    Do not include any text, explanation, or markdown formatting 
    before or after the JSON object. If information for a field is not 
    available, use null."

-----------------------------
7. BEST PRACTICES
-----------------------------
- Whenever your API provider offers a DEDICATED structured output/JSON 
  mode feature (OpenAI's structured outputs, Anthropic's tool use with 
  JSON schemas, Google's response schema configuration), USE IT rather 
  than relying purely on plain-text prompt instructions — these 
  features provide much stronger reliability guarantees.
- Provide an EXPLICIT schema with clear field names and types — don't 
  make the model guess at what fields you want or what format each 
  value should take.
- Include a concrete EXAMPLE of the expected JSON output whenever 
  possible — this is one of the most effective ways to improve JSON 
  formatting reliability, functioning as implicit few-shot guidance.
- Explicitly instruct "no text before or after the JSON" to prevent 
  the model from adding conversational preambles ("Here's the JSON you 
  requested:") that would break automated parsing.
- Define how to handle MISSING or UNCERTAIN data explicitly (typically 
  using `null` for genuinely missing values) rather than leaving this 
  ambiguous, which can lead to inconsistent handling (empty strings 
  vs. omitted fields vs. placeholder text) across different responses.
- ALWAYS validate/parse the returned JSON programmatically on the 
  receiving end with proper error handling (try/catch around your 
  JSON.parse() or equivalent) — even highly reliable models can 
  occasionally produce malformed JSON, especially for very complex 
  nested schemas.
- For NESTED or complex schemas, consider breaking extremely 
  complicated single-schema requests into multiple simpler JSON 
  extraction calls, which tends to improve reliability compared to one 
  extremely complex nested structure requested all at once.

-----------------------------
8. COMMON MISTAKES
-----------------------------
- MISTAKE: Relying purely on natural-language prompt instructions for 
  JSON formatting when a dedicated structured-output API feature is 
  actually available, missing a significant reliability improvement.
  FIX: Always use your provider's dedicated JSON/structured output 
  mode when available, rather than just asking nicely in the prompt.

- MISTAKE: Not providing an explicit schema, leaving the model to 
  guess field names/structure, leading to inconsistent output across 
  multiple runs.
  FIX: Always define an explicit, exact schema for the model to 
  follow.

- MISTAKE: The model adding conversational text before/after the JSON 
  ("Sure, here's the JSON:"), breaking automated parsing that expects 
  pure JSON.
  FIX: Explicitly instruct "no text before or after the JSON object."

- MISTAKE: Not defining how to handle missing/null data, leading to 
  inconsistent representations (sometimes empty string, sometimes 
  omitted field, sometimes placeholder text) across different 
  responses.
  FIX: Explicitly instruct using `null` for missing/unavailable data.

- MISTAKE: Not validating the returned JSON programmatically before 
  using it, assuming it will always be perfectly formatted.
  FIX: Always parse with proper error handling on the receiving 
  application side, regardless of how reliable your chosen model/
  method is.

-----------------------------
9. EXAMPLES (BASIC, INTERMEDIATE, ADVANCED)
-----------------------------

--- BASIC EXAMPLE ---
Prompt:
"Extract the name, email, and phone number from this text, and 
respond ONLY with valid JSON matching this schema: 
{"name": "string", "email": "string", "phone": "string"} 
Do not include any text before or after the JSON. If a field isn't 
present in the text, use null. 

Text: 'Hi, this is Sarah Johnson. You can reach me at 
sarah.j@email.com if you have any questions. Looking forward to 
hearing from you!'"

Expected Output:
{"name": "Sarah Johnson", "email": "sarah.j@email.com", "phone": 
null}

--- INTERMEDIATE EXAMPLE ---
Prompt:
"Analyze the sentiment and key themes of this product review, and 
respond ONLY with valid JSON matching this exact schema: 
{ 
  "sentiment": "positive" | "negative" | "neutral", 
  "confidence": number (0.0 to 1.0), 
  "key_themes": ["array", "of", "short", "theme", "strings"], 
  "would_recommend_product_improvement": boolean 
} 
Do not include any text before or after the JSON object. 

Review: 'This laptop is decent for basic tasks, but the battery life 
is honestly disappointing — barely lasts 4 hours with normal use. The 
screen quality is great though, and it's lightweight enough to carry 
around comfortably.'"

Expected Output:
{"sentiment": "neutral", "confidence": 0.75, "key_themes": ["battery 
life", "screen quality", "portability"], 
"would_recommend_product_improvement": true}

--- ADVANCED EXAMPLE ---
Prompt:
"You are processing structured data for an AI agent orchestration 
system (similar in purpose to a task router within a larger multi-
agent swarm). Given an incoming task description, respond ONLY with 
valid JSON matching this exact nested schema: 
{ 
  "task_category": "coding" | "research" | "writing" | "analysis" | 
"other", 
  "estimated_complexity": "low" | "medium" | "high", 
  "required_capabilities": ["array of strings, e.g., 'code_execution', 
'web_search', 'file_access'"], 
  "suggested_agent_config": { 
    "model_tier": "fast" | "balanced" | "powerful", 
    "max_iterations": number, 
    "requires_human_review": boolean 
  }, 
  "confidence_notes": "string or null if not applicable" 
} 
Do not include any text before or after the JSON object. Use null for 
any field where you have genuinely insufficient information to 
determine a value, rather than guessing. 

Task description: 'Review our production authentication codebase for 
security vulnerabilities, focusing especially on password handling and 
session management, and provide a prioritized list of issues with 
suggested fixes.'"

Expected Output:
{"task_category": "analysis", "estimated_complexity": "high", 
"required_capabilities": ["file_access", "code_execution"], 
"suggested_agent_config": {"model_tier": "powerful", 
"max_iterations": 5, "requires_human_review": true}, 
"confidence_notes": "Security-focused code review; complexity rated 
high due to the security-critical nature of authentication code where 
errors have significant consequences, warranting a more powerful 
model tier and mandatory human review of findings before any fixes 
are applied."}
(Demonstrating correctly structured, valid JSON matching a complex 
nested schema exactly, with no extraneous text, appropriate reasoning 
reflected in the confidence_notes field, and sensible values chosen 
for every field based on the genuinely security-critical and complex 
nature of the described task.)

-----------------------------
10. REUSABLE PROMPT TEMPLATE
-----------------------------
    [YOUR TASK / DATA EXTRACTION OR GENERATION REQUEST]
    
    Respond ONLY with valid JSON matching this exact schema:
    {
      "[field_name_1]": "[type — string/number/boolean]",
      "[field_name_2]": "[type]",
      "[field_name_3]": ["array", "of", "type"],
      "[nested_object_field]": {
        "[sub_field]": "[type]"
      }
    }
    
    Rules:
    - Do NOT include any text, explanation, or markdown formatting 
      before or after the JSON object
    - Use `null` for any field where information is genuinely 
      unavailable or cannot be determined — do not guess or fabricate 
      values
    - Ensure all field names and types exactly match the schema above
    
    [If available, prefer using your API provider's dedicated JSON/
    structured-output mode instead of relying solely on these prompt 
    instructions, for maximum reliability.]
