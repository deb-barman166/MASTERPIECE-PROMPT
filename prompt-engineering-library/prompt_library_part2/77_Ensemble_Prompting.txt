-----------------------------
1. TITLE
-----------------------------
Ensemble Prompting — Combining Multiple Approaches for Superior Results

-----------------------------
2. DEFINITION
-----------------------------
Ensemble Prompting is a technique where MULTIPLE DIFFERENT prompting 
approaches, prompt phrasings, or even different MODELS are used to 
generate independent responses to the SAME task, which are then 
COMBINED — through voting, averaging, synthesis, or selection — to 
produce a final result more reliable than any single approach alone. 
This generalizes and extends the specific pattern of Self-Consistency 
Prompting (file 13, multiple reasoning PATHS from the SAME prompt on 
the SAME model) to the broader practice of combining genuinely 
DIFFERENT prompts, techniques, or models — drawing directly on the 
well-established machine learning principle that ensembles of diverse 
models/approaches typically outperform any single one, since different 
approaches tend to have different, often uncorrelated error patterns.

Think of it like the difference between asking one single expert for 
their opinion (a single approach) versus consulting several genuinely 
different experts — perhaps using different methodologies or coming 
from different specialties — and synthesizing their collective input 
into a final, more robust decision, since each individual expert's 
particular blind spots are less likely to be shared by all of them 
simultaneously.

-----------------------------
3. PURPOSE
-----------------------------
Ensemble Prompting exists to:
- Improve overall RELIABILITY and accuracy by combining multiple 
  independent approaches, reducing the impact of any single approach's 
  specific weaknesses or blind spots.
- Leverage DIFFERENT MODELS' different strengths — some models excel at 
  certain task types, and combining their outputs can produce results 
  better than any single model alone.
- Provide a natural CONFIDENCE SIGNAL — when multiple diverse approaches 
  converge on the same answer, this agreement is meaningful evidence of 
  correctness; when they diverge significantly, this signals genuine 
  ambiguity or difficulty worth flagging.
- Support HIGH-STAKES decisions where the additional cost of running 
  multiple approaches is justified by the value of increased 
  reliability.
- Combine naturally with Self-Consistency (file 13, ensemble within one 
  model/prompt), Debate Prompting (file 28, a structured adversarial 
  form of multi-perspective combination), and Multi-Agent Prompting 
  (file 27) as related manifestations of the broader "combine multiple 
  perspectives for better results" principle.

-----------------------------
4. WHEN TO USE AND BEST MODEL OR LLM
-----------------------------
WHEN TO USE:
- High-stakes decisions or classifications where accuracy justifies the 
  additional cost of running multiple approaches.
- Situations where different available models have known, genuinely 
  different strengths relevant to the task.
- Building robust, production-grade classification or evaluation 
  systems where a single point of failure (one model, one prompt 
  approach) carries meaningful risk.
- Research or benchmarking contexts specifically comparing/combining 
  multiple approaches.

WHEN NOT TO USE:
- Simple, low-stakes tasks where a single well-crafted prompt/model 
  already performs reliably, making the added cost/complexity of 
  ensembling unjustified.
- Extremely latency-sensitive applications where running multiple 
  approaches (sequentially, or even in parallel with added coordination 
  overhead) meaningfully delays the final result.
- Budget-constrained applications where the multiplied cost of running 
  several approaches per query isn't justified by the accuracy gain for 
  your specific use case.

BEST MODELS/APPROACHES FOR ENSEMBLE PROMPTING:
- CROSS-MODEL ensembles (e.g., combining Claude, GPT-4o/4.1/5-class, 
  and Gemini Pro's independent responses to the same question) can 
  surface genuinely different perspectives/error patterns compared to 
  running the same model multiple times, since different providers' 
  models are trained differently and have different characteristic 
  strengths/weaknesses.
- CROSS-PROMPT ensembles (using genuinely different prompt phrasings/
  techniques — e.g., one Zero-Shot attempt, one Few-Shot attempt, one 
  Chain-of-Thought attempt — all on the SAME model) can also produce 
  meaningfully diverse outputs worth combining.
- For COMBINING results, a separate "synthesis" or "judge" prompt 
  (similar to the Judge role in Debate Prompting) is often used to 
  intelligently combine multiple ensemble outputs rather than simple 
  mechanical voting, especially for open-ended (non-multiple-choice) 
  tasks.
- This technique fundamentally requires ORCHESTRATION — running 
  multiple API calls (potentially to different providers) and combining 
  results, typically implemented in application code rather than a 
  single prompt/conversation.

-----------------------------
5. PROMPT FORMULA
-----------------------------
    "Run [TASK] using [APPROACH A / MODEL A], [APPROACH B / MODEL B], 
    and [APPROACH C / MODEL C] independently. Combine the results via 
    [VOTING/SYNTHESIS METHOD] to produce a final, more reliable answer."

-----------------------------
6. PROMPT STRUCTURE
-----------------------------
    1. Task Definition — the specific question/task to be answered by 
       multiple approaches.
    2. Ensemble Members — the specific set of different approaches, 
       prompts, or models to be used (each genuinely different from the 
       others, not near-duplicates).
    3. Independent Execution — each ensemble member generates its 
       response WITHOUT seeing the others' outputs (to preserve genuine 
       independence, avoiding one approach simply copying/anchoring on 
       another).
    4. Combination Method — how the multiple outputs get merged: 
       majority voting (for discrete answers), averaging (for numeric 
       outputs), or synthesis by a separate "judge" prompt (for open-
       ended outputs).
    5. Confidence/Agreement Reporting — noting how much the different 
       approaches agreed or diverged, as a signal of overall confidence 
       in the final combined result.

Example skeleton:
    "Task: [QUESTION/PROBLEM]. 
    
    Run this independently using: 
    - Approach A: [e.g., Model 1 with Zero-Shot prompting] 
    - Approach B: [e.g., Model 2 with Chain-of-Thought prompting] 
    - Approach C: [e.g., Model 3 with Few-Shot prompting] 
    
    Combine the [N] independent results via [majority vote / synthesis 
    by a judge prompt]. Report the level of agreement across 
    approaches as a confidence signal."

-----------------------------
7. BEST PRACTICES
-----------------------------
- Ensure GENUINE INDEPENDENCE between ensemble members — each approach/
  model should generate its response without seeing the others' 
  outputs, preserving the value of truly diverse, uncorrelated 
  perspectives.
- Choose ensemble members with MEANINGFULLY DIFFERENT characteristics 
  (different models, different prompting techniques, different 
  underlying approaches) rather than near-duplicate variations that 
  won't actually surface different error patterns.
- For DISCRETE/categorical answers, majority voting is often sufficient 
  for combination; for OPEN-ENDED outputs (essays, code, analysis), a 
  dedicated synthesis/judge step (similar to Debate Prompting's Judge 
  role) that intelligently combines the best elements is typically more 
  valuable than naive mechanical merging.
- Report the AGREEMENT LEVEL across ensemble members as a genuine 
  confidence signal — strong agreement across diverse approaches is 
  meaningful evidence; significant disagreement should be flagged as a 
  sign of genuine difficulty/ambiguity worth additional scrutiny, not 
  papered over.
- Weigh the COST/BENEFIT explicitly — ensembling multiplies your 
  computational cost by the number of ensemble members; reserve this 
  technique for cases where the accuracy/reliability improvement 
  genuinely justifies this multiplied cost.
- For CROSS-MODEL ensembles specifically, be aware that different 
  providers may have different API access requirements/costs, adding 
  practical implementation complexity beyond same-provider approaches.
- Consider whether a SIMPLER technique (Self-Consistency within one 
  model, or a single well-optimized prompt via Prompt Optimization) 
  might achieve most of the reliability benefit at meaningfully lower 
  cost/complexity before committing to full multi-model ensembling.

-----------------------------
8. COMMON MISTAKES
-----------------------------
- MISTAKE: Ensemble members that aren't genuinely independent (one 
  approach sees and is influenced by another's output), reducing the 
  diversity benefit that makes ensembling valuable.
  FIX: Always generate each ensemble member's response independently, 
  without cross-contamination.

- MISTAKE: Choosing ensemble members that are too similar to each other 
  (e.g., the same model with only trivially different prompt wording), 
  providing little genuine diversity benefit.
  FIX: Choose meaningfully different models/approaches/techniques for 
  genuine ensemble diversity.

- MISTAKE: Using naive mechanical combination (simple averaging/
  concatenation) for open-ended outputs where intelligent synthesis 
  would produce a genuinely better combined result.
  FIX: Use a dedicated synthesis/judge step for combining open-ended, 
  non-categorical outputs.

- MISTAKE: Not reporting or acting on disagreement levels across 
  ensemble members, missing a valuable confidence/uncertainty signal.
  FIX: Explicitly track and report agreement/disagreement as part of 
  the final result.

- MISTAKE: Applying expensive multi-model ensembling to tasks where a 
  much simpler, cheaper approach would already provide sufficient 
  reliability.
  FIX: Reserve ensembling for genuinely high-stakes cases; consider 
  simpler alternatives first.

-----------------------------
9. EXAMPLES (BASIC, INTERMEDIATE, ADVANCED)
-----------------------------

--- BASIC EXAMPLE ---
Setup:
"Task: Determine if this product review is Positive, Negative, or 
Neutral: 'The product works fine but shipping took way longer than 
expected.' 

Run independently: 
- Approach A: Claude, zero-shot classification 
- Approach B: GPT-4o, zero-shot classification 
- Approach C: Gemini Pro, zero-shot classification 

Combine via majority vote."

Expected Output:
If 2 of 3 models classify this as "Neutral" (a genuinely mixed review 
— positive on product, negative on shipping) and 1 classifies it as 
"Negative" (weighing the shipping complaint more heavily), the majority 
vote result would be "Neutral," with the 2-out-of-3 agreement providing 
a reasonable (though not unanimous) confidence signal, correctly 
flagging this as a genuinely mixed/borderline case rather than a 
strongly clear-cut sentiment.

--- INTERMEDIATE EXAMPLE ---
Setup:
"Task: Estimate the most likely root cause of this production incident: 
[incident description involving intermittent API timeouts under high 
load]. 

Run independently: 
- Approach A: Claude with Chain-of-Thought reasoning 
- Approach B: GPT-4o with ReAct-style reasoning, given access to 
relevant log-search tools 
- Approach C: A domain-expert-persona prompt (Role Prompting) asking a 
model to reason as a senior site reliability engineer 

Combine via a synthesis step: present all 3 independent diagnoses to a 
4th 'judge' prompt, asking it to identify areas of agreement, 
meaningful disagreement, and synthesize a final most-likely diagnosis 
with appropriate confidence level."

Expected Output:
Three independent diagnostic attempts (potentially converging on 
similar root causes like connection pool exhaustion, or surfacing 
genuinely different hypotheses like a specific downstream dependency 
issue vs. a resource limit issue), followed by a synthesis step that 
identifies where the independent approaches agreed (increasing 
confidence in that shared conclusion) and where they diverged (flagging 
areas needing further investigation rather than false certainty) — 
producing a final diagnosis with an honestly-calibrated confidence 
level based on the actual cross-approach agreement observed.

--- ADVANCED EXAMPLE ---
Setup:
"Task: Evaluate whether this proposed system architecture change (a 
migration from a single shared SQLite memory store to a distributed 
Redis-based approach for a 50-agent multi-agent system) is sound before 
committing significant implementation effort. 

Run independently: 
- Approach A: Claude Opus, using Self-Critique Prompting (acting as a 
skeptical senior architect) 
- Approach B: GPT-4o, using Tree-of-Thoughts to explore multiple 
alternative migration approaches before evaluating this specific one 
- Approach C: Gemini Pro, using Knowledge-Grounded Prompting combined 
with live search for current best practices on Redis-based multi-agent 
memory architectures 

Combine via synthesis: present all 3 independent evaluations to a 
dedicated synthesis prompt (a 4th call), explicitly asking it to: (1) 
identify concerns raised by 2+ of the 3 approaches (higher-confidence 
issues), (2) identify concerns raised by only 1 approach (worth noting 
but lower confidence), (3) produce a final overall recommendation with 
an honestly-stated confidence level based on the degree of cross-
approach convergence."

Expected Output:
Three genuinely independent, differently-generated evaluations of the 
proposed architecture change (potentially all converging on a shared 
concern like connection management overhead at 50-agent scale, while 
each also surfacing some unique considerations specific to their 
distinct reasoning approach), synthesized into a final report that 
distinguishes HIGH-CONFIDENCE issues (raised independently by multiple 
approaches, suggesting genuine importance) from LOWER-CONFIDENCE, 
single-approach observations (still worth noting but not independently 
corroborated) — providing a genuinely more robust, well-calibrated 
architectural assessment than any single evaluation approach alone 
would have produced, appropriate for a decision significant enough to 
justify the substantial multi-approach evaluation cost.

10. REUSABLE PROMPT TEMPLATE
-----------------------------
    Task: [YOUR QUESTION/PROBLEM]
    
    Run this independently using [N] genuinely different approaches:
    - Approach A: [SPECIFIC MODEL/PROMPTING TECHNIQUE]
    - Approach B: [DIFFERENT MODEL/PROMPTING TECHNIQUE]
    - Approach C: [DIFFERENT MODEL/PROMPTING TECHNIQUE]
    
    Ensure each approach generates its response independently, without 
    seeing the others' outputs.
    
    Combine the results via: [majority vote, for discrete answers / a 
    dedicated synthesis-judge step, for open-ended answers], explicitly 
    noting:
    - Areas where approaches agreed (higher confidence)
    - Areas where approaches diverged (lower confidence, worth further 
    scrutiny)
    
    Provide a final answer with an honestly-calibrated confidence level 
    based on the observed cross-approach agreement.
