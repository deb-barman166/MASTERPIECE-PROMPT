-----------------------------
1. TITLE
-----------------------------
Meta Prompting — Using AI to Design and Improve Prompts

-----------------------------
2. DEFINITION
-----------------------------
Meta prompting is the technique of using an LLM to generate, analyze, 
improve, or reason ABOUT prompts themselves — rather than using it to 
directly answer a question or complete a task. Instead of asking "do 
X," you ask "help me design the best possible prompt for doing X," 
turning the model into a prompt-engineering collaborator/consultant. 
This is a foundationally recursive technique — using the tool to 
improve how you use the tool — and represents the conceptual bridge 
between manually crafting individual prompts (everything covered so 
far in this library) and more systematic, semi-automated approaches to 
prompt design (Prompt Optimization, Automatic Prompt Engineering, and 
related techniques covered later in this section).

Think of it like the difference between asking a skilled writer to 
write your essay for you versus asking that same skilled writer to 
review and help you improve the ESSAY PROMPT/ASSIGNMENT you're about 
to give to someone else — meta prompting operates one level up, 
focused on the instrument (the prompt) rather than the direct output.

-----------------------------
3. PURPOSE
-----------------------------
Meta prompting exists to:
- Leverage the model's own understanding of effective prompting 
  patterns (gained from extensive training on prompt-engineering-
  related content) to improve YOUR prompts before you use them.
- Save TIME and effort in prompt design by generating a strong first 
  draft prompt rather than starting from a completely blank page.
- Diagnose WHY a prompt isn't producing the desired results, since the 
  model can often identify ambiguities or missing elements a human 
  might overlook in their own writing.
- Support systematic prompt IMPROVEMENT over time — using the model to 
  refine an existing prompt template based on observed shortcomings.
- Serve as the conceptual foundation for more advanced automated 
  techniques (Automatic Prompt Engineering, DSPy-Style Prompting) 
  covered later in this section, which formalize and scale this same 
  underlying idea.

-----------------------------
4. WHEN TO USE AND BEST MODEL OR LLM
-----------------------------
WHEN TO USE:
- Designing a new prompt for an important or recurring task, where 
  getting it right matters more than the effort of a design pass.
- Diagnosing why an existing prompt isn't producing satisfactory 
  results.
- Building a prompt library or template system (directly relevant to 
  Template Prompting, file 43) where you want professionally-designed 
  starting points.
- Learning prompt engineering itself — asking the model to explain WHY 
  certain prompt structures work better than others is a genuinely 
  effective learning method.

WHEN NOT TO USE:
- Simple, one-off tasks where the effort of meta-prompting exceeds the 
  value of prompt optimization for a single use.
- When you already have a well-tested, working prompt template and 
  don't have a specific problem to solve.
- As a substitute for actually TESTING your prompts with real inputs — 
  meta prompting can suggest improvements, but only real usage reveals 
  whether they actually work as intended.

BEST MODELS FOR META PROMPTING:
- Claude — excellent for meta-prompting given strong understanding of 
  its own (and other models') behavior patterns and genuinely thoughtful 
  analysis of prompt design trade-offs.
- GPT-4o/4.1/5-class — strong meta-prompting capability, well-versed in 
  documented prompt engineering best practices.
- Gemini Pro/Ultra — capable meta-prompting, particularly useful when 
  designing prompts specifically intended for Gemini models given 
  potential self-knowledge of its own tendencies.
- IMPORTANT NUANCE: a model is generally better at meta-prompting FOR 
  ITSELF or models similar to itself than for genuinely different model 
  families, since different models have different specific quirks/
  preferences (e.g., Claude's strong XML-tag responsiveness vs. other 
  models' different conventions) that the model being asked may not 
  fully know about other systems.

-----------------------------
5. PROMPT FORMULA
-----------------------------
    "I want a prompt that achieves [GOAL] for [TARGET MODEL]. Design 
    an effective prompt for this, explaining your design choices." OR 
    "Here's my current prompt: [PROMPT]. It's not producing [DESIRED 
    RESULT]. Diagnose why and suggest improvements."

-----------------------------
6. PROMPT STRUCTURE
-----------------------------
    1. Task Goal — what the eventual prompt needs to accomplish.
    2. Target Model (if known) — which specific model/model family the 
       prompt will be used with, since different models have different 
       optimal conventions.
    3. Constraints — any specific requirements the prompt must satisfy 
       (length limits, must produce JSON output, must work across 
       multiple model providers).
    4. Either: Design Request (build a new prompt from scratch) OR 
       Diagnostic Request (analyze an existing underperforming prompt).
    5. Explanation Requirement — ask for reasoning behind design 
       choices, which both validates the suggestions and builds your 
       own prompt engineering skill over time.

Example skeleton (Design):
    "I need a prompt that will [GOAL], intended for use with [TARGET 
    MODEL]. 
    Requirements: [CONSTRAINTS] 
    Design an effective prompt for this, explaining your key design 
    choices."

Example skeleton (Diagnostic):
    "Here's my current prompt: 
    [EXISTING PROMPT] 
    
    It's producing [ACTUAL UNSATISFACTORY RESULT] instead of [DESIRED 
    RESULT]. 
    Diagnose likely causes and suggest specific improvements."

-----------------------------
7. BEST PRACTICES
-----------------------------
- Specify the TARGET MODEL when known — a prompt optimized for Claude's 
  XML-tag responsiveness may need adjustment for a different model's 
  preferred conventions.
- Provide REAL EXAMPLES of unsatisfactory output when doing diagnostic 
  meta-prompting — "it's not working well" is far less useful than 
  showing the actual disappointing output alongside what you wanted 
  instead.
- Ask for the REASONING behind suggested prompt design choices, not 
  just the improved prompt itself — this helps you evaluate whether the 
  suggestions make sense and builds transferable prompt engineering 
  skill.
- Treat meta-prompted suggestions as a strong DRAFT to test, not a 
  guaranteed final answer — always validate the suggested prompt 
  against real inputs before relying on it for important use cases.
- For RECURRING task types, invest more heavily in meta-prompting to 
  develop a genuinely well-designed Template Prompting (file 43) 
  starting point, since the design effort pays off across many future 
  uses.
- Combine with Self-Critique principles by asking the model to also 
  identify WEAKNESSES or edge cases in its own suggested prompt design, 
  not just present it as flawless.
- Iterate — meta-prompting isn't necessarily a one-shot process; use 
  initial suggestions, test them, then return with real results for 
  further refinement.

-----------------------------
8. COMMON MISTAKES
-----------------------------
- MISTAKE: Not specifying the target model, resulting in generic 
  suggestions that might not leverage model-specific strengths (like 
  Claude's XML tag responsiveness).
  FIX: Specify the target model/model family when known.

- MISTAKE: Vague diagnostic requests ("this prompt isn't working well") 
  without showing actual unsatisfactory output, limiting the model's 
  ability to diagnose the specific problem.
  FIX: Always provide concrete examples of the actual disappointing 
  output when seeking diagnostic help.

- MISTAKE: Treating meta-prompted suggestions as guaranteed-correct 
  without testing them against real inputs.
  FIX: Always validate suggested prompts through actual testing before 
  relying on them.

- MISTAKE: Not asking for reasoning behind suggestions, missing the 
  opportunity to build genuine prompt engineering understanding over 
  time.
  FIX: Always request explanation of design choices alongside 
  suggested improvements.

- MISTAKE: Using meta-prompting for trivial, one-off tasks where the 
  design effort exceeds the value of optimization.
  FIX: Reserve more intensive meta-prompting effort for important or 
  recurring task types.

-----------------------------
9. EXAMPLES (BASIC, INTERMEDIATE, ADVANCED)
-----------------------------

--- BASIC EXAMPLE ---
Prompt:
"I need a prompt that will reliably get an LLM to write product 
descriptions in a consistent format (name, 2-sentence description, 3 
bullet-point features), intended for use with GPT-4o. Design an 
effective prompt for this, explaining your key design choices."

Expected Output:
A well-designed prompt template incorporating clear structure 
(possibly Markdown headers or explicit format specification per Format-
Constrained Prompting), with an explanation of why this structure was 
chosen (e.g., explicit format specification reduces ambiguity, a 
concrete example would further improve consistency).

--- INTERMEDIATE EXAMPLE ---
Prompt:
"Here's my current prompt for classifying customer support tickets: 
'Look at this message and tell me what category it is: Billing, 
Technical, or General.' 

It's producing inconsistent results — sometimes it gives me a full 
paragraph explanation instead of just the category, and sometimes it 
seems to force tickets into 'General' when they don't clearly fit 
Billing or Technical. Diagnose likely causes and suggest specific 
improvements, explaining your reasoning."

Expected Output:
A diagnosis identifying multiple likely issues: (1) no explicit output 
format instruction, causing inconsistent verbosity — fix: explicitly 
request "respond with only the category label"; (2) no "Other" catch-
all category, forcing awkward fits into "General" — fix: add an 
explicit "Other" option or refine category definitions with brief 
clarifying descriptions; (3) possibly benefiting from Few-Shot examples 
to improve classification consistency — each diagnosed issue paired 
with a specific, explained fix, likely culminating in a revised prompt 
incorporating all suggested improvements.

--- ADVANCED EXAMPLE ---
Prompt:
"I'm building a reusable prompt template (to be used across many 
different code review requests) for reviewing Python code specifically 
for security vulnerabilities in a solo-developer workflow, intended for 
use with Claude via the API. 

Requirements: 
- Must work well for reviewing code snippets of varying size (a single 
function up to a few hundred lines) 
- Output needs to be structured enough to parse programmatically 
(I'll be running this across many files in a pipeline) 
- Should minimize false positives on non-security issues (I have a 
separate style linter already) 

Design an effective, reusable prompt template for this, explaining your 
key design choices. Also, proactively identify any weaknesses or edge 
cases in your suggested design that I should be aware of and test for."

Expected Output:
A well-designed, reusable prompt template incorporating: a clear role 
declaration (security-focused reviewer), explicit scope boundaries 
(security only, not style, addressing the stated false-positive 
concern), a structured JSON output schema (per Schema Prompting 
principles, addressing the programmatic parsing requirement), and 
severity classification — with explained reasoning for each design 
choice tied directly to the stated requirements (e.g., "the explicit 
JSON schema ensures consistent, parseable output across your pipeline 
regardless of code snippet size") — followed by proactive identification 
of potential weaknesses (e.g., "this template may still occasionally 
flag borderline style/security overlap issues like input validation, 
which sits at the boundary between style and security — you may want 
to test this specific boundary case and refine the scope definition if 
it causes noise in your pipeline") — demonstrating meta-prompting that 
goes beyond just generating a prompt to also anticipating its practical 
limitations.
