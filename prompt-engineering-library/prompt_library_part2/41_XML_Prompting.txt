-----------------------------
1. TITLE
-----------------------------
XML Prompting — Structuring Prompts With Tag-Based Markup

-----------------------------
2. DEFINITION
-----------------------------
XML prompting is a technique where you organize a prompt's components 
using XML-style tags (<tag_name>content</tag_name>) to create 
unambiguous, nested, machine-and-model-readable boundaries between 
different parts of your instructions — such as <role>, <context>, 
<task>, <examples>, and <constraints>. Unlike general Structured 
Prompting (which can use Markdown, numbered lists, or XML 
interchangeably), XML Prompting specifically leverages TAG-BASED 
markup with opening/closing tags and supports NESTING (tags within 
tags), making it especially powerful for deeply hierarchical or 
multi-layered instructions.

Think of it like the difference between writing a legal contract as 
one flowing paragraph versus using clearly labeled, nested clauses 
and sub-clauses (Section 1, Subsection 1.a, Subsection 1.b) — the tag 
structure itself carries meaning about how pieces relate to and 
contain one another, not just that they're separate.

-----------------------------
3. PURPOSE
-----------------------------
XML prompting exists to:
- Provide UNAMBIGUOUS boundaries between different prompt components, 
  leaving zero doubt about where one section ends and another begins.
- Support genuine NESTING/HIERARCHY — a <examples> tag can contain 
  multiple <example> tags, each with its own <input> and <output> sub-
  tags, representing structure that flat Markdown headers struggle to 
  express cleanly.
- Leverage the fact that models (Claude in particular) are extensively 
  trained on and specifically optimized for parsing XML-tagged prompts 
  accurately.
- Enable precise, targeted REFERENCING within a long prompt (e.g., "as 
  defined in the <constraints> section above") that stays unambiguous 
  even in very long, complex prompts.
- Support round-trip consistency for programmatically generated 
  prompts, since XML has strict, well-defined syntax rules that make 
  automated construction and validation straightforward.

-----------------------------
4. WHEN TO USE AND BEST MODEL OR LLM
-----------------------------
WHEN TO USE:
- Complex prompts with several distinct components that benefit from 
  explicit nesting (e.g., multiple examples each with their own 
  labeled sub-parts).
- Working specifically with Claude models, where Anthropic's own 
  documentation and training approach specifically favors and 
  reinforces XML-tag comprehension.
- Programmatically generated prompts where you need reliable, 
  parseable structure for inserting dynamic content into fixed 
  templates.
- Long, multi-part prompts where you want to be able to reference a 
  specific earlier section unambiguously.
- Any task combining several other techniques from this library (Few-
  Shot examples + Context + Constraints) that benefits from very clear 
  delineation.

WHEN NOT TO USE:
- Simple, single-part prompts where tag overhead adds nothing.
- Casual conversational exchanges where XML tags would feel 
  unnaturally technical/rigid.
- When working with models that show little specific XML-training 
  benefit — in such cases, Markdown Prompting (file 42) may feel more 
  natural without losing much clarity.

BEST MODELS FOR XML PROMPTING:
- Claude — the standout choice; Anthropic explicitly recommends XML 
  tags as a preferred structuring method in official prompting 
  documentation, and Claude models are specifically trained to parse 
  and respect these boundaries with high reliability.
- GPT-4o/4.1/5-class — handles XML-tagged prompts well, though it 
  responds comparably well to Markdown-style structuring too.
- Gemini Pro/Ultra — capable of parsing XML-structured prompts 
  accurately, though Google's own documentation often favors Markdown/
  JSON for its ecosystem.
- DeepSeek / Qwen — generally capable XML parsing, particularly 
  reliable for coding-adjacent structured tasks.
- Mistral / Llama — capable of following XML structure, though 
  benefits are less pronounced than with Claude specifically; test 
  before assuming strong nested-tag comprehension in smaller variants.

-----------------------------
5. PROMPT FORMULA
-----------------------------
    <role>[ROLE]</role>
    <context>[BACKGROUND]</context>
    <task>[INSTRUCTION]</task>
    <examples>
      <example>
        <input>[...]</input>
        <output>[...]</output>
      </example>
    </examples>
    <constraints>[RULES]</constraints>

-----------------------------
6. PROMPT STRUCTURE
-----------------------------
    1. Top-Level Tags — major sections like <role>, <context>, <task>, 
       <constraints>, <output_format>.
    2. Nested Sub-Tags — where a section naturally contains repeated 
       or hierarchical items (e.g., multiple <example> blocks inside 
       an <examples> parent tag).
    3. Consistent Naming — the same concept should always use the 
       same tag name throughout a single prompt (don't call it 
       <context> in one place and <background> in another).
    4. Closing Tags — every opening tag must have a matching closing 
       tag; unclosed tags can confuse parsing.
    5. Content Inside Tags — the actual instruction/data content, 
       written normally within each tag's boundaries.

Example skeleton:
    "<role>You are a [ROLE].</role>
    <context>[BACKGROUND INFORMATION]</context>
    <task>[WHAT TO DO]</task>
    <examples>
      <example>
        <input>[SAMPLE INPUT]</input>
        <output>[SAMPLE OUTPUT]</output>
      </example>
    </examples>
    <constraints>
      <constraint>[RULE 1]</constraint>
      <constraint>[RULE 2]</constraint>
    </constraints>
    <output_format>[DESIRED RESPONSE STRUCTURE]</output_format>"

-----------------------------
7. BEST PRACTICES
-----------------------------
- Use DESCRIPTIVE, semantically meaningful tag names (<context>, 
  <task>) rather than generic ones (<section1>, <data>).
- Keep tag naming CONSISTENT throughout the entire prompt — pick one 
  name per concept and stick with it.
- Use NESTING deliberately when content is genuinely hierarchical 
  (multiple examples, multiple constraints) rather than flattening 
  everything into top-level tags unnecessarily.
- Always CLOSE every tag you open — even though models are often 
  forgiving of minor syntax issues, clean, valid XML produces the most 
  reliable parsing.
- For Claude specifically, feel free to ask the model to REFERENCE a 
  specific tagged section directly (e.g., "using the criteria in 
  <constraints>, evaluate...") since this leverages the model's 
  strong tag-comprehension training.
- Don't over-nest — 2-3 levels of nesting is usually sufficient; 
  excessive nesting depth can reduce clarity rather than improve it.
- When requesting XML-tagged OUTPUT (not just input), provide an 
  explicit example of the exact tag structure you want returned.

-----------------------------
8. COMMON MISTAKES
-----------------------------
- MISTAKE: Inconsistent tag naming for the same concept across a 
  single prompt (<context> vs. <background> vs. <info>).
  FIX: Choose one tag name per concept and use it consistently 
  throughout.

- MISTAKE: Leaving tags unclosed or mismatched (opening <task> but 
  closing </instruction>), creating ambiguous structure.
  FIX: Always carefully match opening and closing tags.

- MISTAKE: Flattening genuinely hierarchical content (multiple 
  examples with sub-parts) into repetitive top-level tags instead of 
  using proper nesting.
  FIX: Nest child tags inside a parent container tag when content is 
  naturally hierarchical.

- MISTAKE: Using XML tags for extremely simple, single-part prompts 
  where the overhead adds no real clarity benefit.
  FIX: Reserve XML structuring for genuinely complex, multi-part 
  prompts.

- MISTAKE: Assuming ALL models benefit equally from XML tags the way 
  Claude specifically does, without testing.
  FIX: Verify your chosen model actually responds well to XML 
  structure; consider Markdown as an alternative if not.

9. EXAMPLES (BASIC, INTERMEDIATE, ADVANCED)
-----------------------------

--- BASIC EXAMPLE ---
Prompt:
"<task>Write a one-sentence summary.</task>
<context>The text is a news article about a new AI chip 
announcement.</context>
<constraints>Maximum 20 words.</constraints>"

Expected Output:
A single, concise sentence (20 words or fewer) accurately summarizing 
an AI chip announcement, correctly synthesizing all three tagged 
sections.

--- INTERMEDIATE EXAMPLE ---
Prompt:
"<role>You are a Python tutor for beginners.</role>
<task>Explain what a dictionary is in Python.</task>
<examples>
  <example>
    <input>Explain what a list is.</input>
    <output>A list is like a numbered row of boxes, where each box 
holds one item, and you can access any box using its position 
number.</output>
  </example>
</examples>
<constraints>
  <constraint>Use a simple real-world analogy, similar in style to 
the example above.</constraint>
  <constraint>Keep it under 60 words.</constraint>
</constraints>"

Expected Output:
An explanation of Python dictionaries using a real-world analogy 
(e.g., comparing it to a real dictionary or labeled filing cabinet 
where you look things up by name rather than position), matching the 
simple, friendly style demonstrated in the nested example, staying 
under 60 words.

--- ADVANCED EXAMPLE ---
Prompt:
"<role>You are a senior ML engineer reviewing a teammate's model 
training script.</role>
<context>
  <project>Image classification model using PyTorch</project>
  <concern>Training loss is decreasing but validation accuracy has 
plateaued after epoch 5</concern>
</context>
<code_to_review>
  [training loop code pasted here]
</code_to_review>
<task>Diagnose the likely cause of this plateau and suggest a 
fix.</task>
<constraints>
  <constraint>Consider overfitting as a primary hypothesis before 
other explanations</constraint>
  <constraint>Provide a specific, testable code change</constraint>
</constraints>
<output_format>
  <diagnosis>[likely cause]</diagnosis>
  <evidence>[what in the code/symptoms supports this]</evidence>
  <fix>[specific code-level suggestion]</fix>
</output_format>"

Expected Output:
A response using the exact nested output_format structure requested, 
with <diagnosis> correctly identifying overfitting as the likely 
cause (decreasing training loss + plateaued validation accuracy is a 
classic overfitting signature), <evidence> citing this specific 
pattern from the described symptoms, and <fix> providing a concrete 
suggestion (e.g., adding dropout, data augmentation, or early 
stopping) — demonstrating correct parsing and response to deeply 
nested, multi-level XML structure.
