-----------------------------
1. TITLE
-----------------------------
Markdown Prompting — Structuring Prompts With Headers and Lightweight 
Syntax

-----------------------------
2. DEFINITION
-----------------------------
Markdown prompting is a technique where you organize a prompt (and 
often request output) using Markdown syntax — headers (#, ##, ###), 
bullet points, numbered lists, bold/italic emphasis, and code blocks — 
to create visually clear, human-readable structure. Compared to XML 
Prompting (which uses explicit tag pairs and is especially strong for 
nesting), Markdown is LIGHTER-WEIGHT, more universally familiar 
(nearly everyone who writes technical content already knows Markdown), 
and renders natively as clean, readable formatting in most modern chat 
interfaces and documentation tools.

Think of it like the difference between writing a formal legal 
document with XML-style nested clauses versus writing a clean, 
well-organized blog post or README file with clear headers and 
bullet points — both create structure, but Markdown favors readability 
and familiarity, while XML favors precision and nesting.

-----------------------------
3. PURPOSE
-----------------------------
Markdown prompting exists to:
- Provide clear structural organization using syntax that's already 
  universally familiar to virtually anyone who writes technical 
  content, requiring no special learning curve.
- Produce OUTPUT that renders natively and attractively in chat 
  interfaces, documentation systems, and note-taking apps (GitHub, 
  Notion, Obsidian, most chat UIs) without any additional conversion.
- Organize prompts with a natural VISUAL HIERARCHY (headers of 
  different levels) that mirrors how people already structure written 
  documents.
- Balance structure and readability — less rigid/verbose than XML tags 
  while still providing meaningfully clearer organization than plain 
  flowing prose.
- Serve as the most common and practical DEFAULT structuring choice 
  for everyday prompts that need some organization but not deep 
  nesting.

-----------------------------
4. WHEN TO USE AND BEST MODEL OR LLM
-----------------------------
WHEN TO USE:
- Everyday complex prompts needing clear sections but not deep, 
  multi-level nesting.
- Any task where the OUTPUT itself should be Markdown-formatted for 
  direct use in documentation, READMEs, notes, or reports (highly 
  relevant to generating guides, documentation, or structured 
  reference material).
- Situations where human readability of the prompt itself matters 
  (e.g., prompts that will be reviewed or edited by other people, not 
  just consumed by a model).
- General-purpose structuring across virtually any model, given 
  Markdown's broad, consistent support.

WHEN NOT TO USE:
- Deeply nested or hierarchical content where Markdown headers alone 
  can't cleanly express the relationships (XML Prompting handles this 
  better).
- Programmatic prompt generation requiring strict, parseable syntax 
  rules (Markdown has more informal/flexible syntax than XML, making 
  it less ideal for strict automated parsing of the prompt structure 
  itself).
- Extremely simple, single-line prompts where any structuring is 
  unnecessary overhead.

BEST MODELS FOR MARKDOWN PROMPTING:
- GPT-4o/4.1/5-class — excellent Markdown comprehension and 
  generation, very natural fit given widespread Markdown use across 
  its training data and typical use cases.
- Claude — strong Markdown handling for both input structure and 
  output generation, though Anthropic's specific guidance often 
  additionally recommends XML for maximum precision on complex 
  prompts.
- Gemini Pro/Ultra — strong native Markdown support, well-integrated 
  with Google's documentation-style formatting conventions.
- DeepSeek / Qwen — reliable Markdown generation, particularly for 
  technical/coding documentation output.
- Mistral / Llama / virtually all modern instruction-tuned models — 
  Markdown is perhaps the most universally well-supported structuring 
  convention across the entire LLM landscape, given its ubiquity in 
  training data (READMEs, documentation, forums, technical writing).

-----------------------------
5. PROMPT FORMULA
-----------------------------
    ## Role
    [ROLE]
    ## Context
    [BACKGROUND]
    ## Task
    [INSTRUCTION]
    ## Constraints
    - [RULE 1]
    - [RULE 2]

-----------------------------
6. PROMPT STRUCTURE
-----------------------------
    1. Top-Level Headers (##) — major prompt sections (Role, Context, 
       Task, Constraints, Output Format).
    2. Sub-Headers (###) — for further breakdown within a major 
       section, if needed.
    3. Bullet/Numbered Lists — for enumerable items (constraints, 
       steps, examples) within any section.
    4. Bold/Italic Emphasis — to highlight especially critical words 
       or phrases (use sparingly for genuine emphasis, not decoration).
    5. Code Blocks (```) — for any code, data, or content that should 
       be preserved exactly as-is, without Markdown re-interpretation.

Example skeleton:
    "## Role
    [ROLE DESCRIPTION]
    
    ## Context
    [BACKGROUND INFO]
    
    ## Task
    [SPECIFIC INSTRUCTION]
    
    ## Constraints
    - [CONSTRAINT 1]
    - [CONSTRAINT 2]
    
    ## Output Format
    [DESIRED STRUCTURE]"

-----------------------------
7. BEST PRACTICES
-----------------------------
- Use HEADER LEVELS consistently and logically (## for major sections, 
  ### for sub-sections) rather than randomly varying header depth.
- Use bullet points for genuinely PARALLEL/enumerable items 
  (constraints, features, steps) rather than forcing prose into 
  artificial bullet form.
- Use CODE BLOCKS (```) for any content that must be preserved exactly 
  — actual code, exact text to be processed, or data — since this 
  visually and semantically signals "don't reformat this."
- Reserve BOLD/ITALIC for genuine emphasis on critical instructions 
  (e.g., "**Do not** include any personal opinions") rather than 
  decorative overuse.
- If you want Markdown-formatted OUTPUT specifically, say so explicitly 
  ("format your response in Markdown with headers") since not every 
  context defaults to rendering or expecting Markdown.
- For prompts that will be read by both humans (reviewing/editing the 
  prompt) and models, Markdown's dual readability is a genuine 
  advantage over more technical XML tags.
- Keep header text SHORT and descriptive, mirroring good documentation 
  practices.

-----------------------------
8. COMMON MISTAKES
-----------------------------
- MISTAKE: Inconsistent or illogical header hierarchy (jumping from ## 
  to #### without a clear reason, or using headers for non-structural 
  emphasis).
  FIX: Use a consistent, logical header hierarchy throughout.

- MISTAKE: Forcing genuinely flowing, narrative content into 
  unnecessary bullet points, fragmenting ideas that would read better 
  as connected prose.
  FIX: Reserve bullets for genuinely parallel/enumerable items.

- MISTAKE: Not using code blocks for actual code or exact-text content, 
  risking the model "helpfully" reformatting or reinterpreting content 
  that should be preserved exactly.
  FIX: Always wrap code/exact content in code blocks (```).

- MISTAKE: Assuming the model will output Markdown formatting without 
  being explicitly asked to, when the context doesn't already imply 
  it.
  FIX: Explicitly request Markdown-formatted output when that's what 
  you need.

- MISTAKE: Overusing bold/italic emphasis throughout a prompt, diluting 
  its impact when everything is emphasized.
  FIX: Reserve emphasis for genuinely critical instructions only.

-----------------------------
9. EXAMPLES (BASIC, INTERMEDIATE, ADVANCED)
-----------------------------

--- BASIC EXAMPLE ---
Prompt:
"## Task
Write a short bio for a developer portfolio.

## Constraints
- Under 50 words
- Mention Python and AI as key skills
- Friendly, approachable tone"

Expected Output:
A concise (under 50 words) portfolio bio that mentions Python and AI 
skills with a friendly, approachable tone, correctly incorporating 
all listed constraints.

--- INTERMEDIATE EXAMPLE ---
Prompt:
"## Role
You are a technical documentation writer.

## Context
This is for a Python library's README file, targeting developers 
who are already comfortable with Python but new to this specific 
library.

## Task
Write an 'Installation' section.

## Constraints
- Include a code block showing the pip install command
- Mention Python version requirements (3.9+)
- Keep it under 80 words total

## Output Format
Use Markdown with a `## Installation` header, a brief sentence, then 
a code block."

Expected Output:
A correctly Markdown-formatted "## Installation" section with a 
proper code block containing the pip install command, a mention of 
the 3.9+ Python requirement, and total length under 80 words — 
demonstrating the model both parsed a Markdown-structured PROMPT and 
correctly produced Markdown-structured OUTPUT matching the specified 
format.

--- ADVANCED EXAMPLE ---
Prompt:
"## Role
You are a senior data scientist mentoring a student new to machine 
learning.

## Context
The student has built a classification model that achieves 98% 
training accuracy but only 71% test accuracy.

### Student's Code Snippet
```python
model.fit(X_train, y_train, epochs=100)
```

## Task
Explain what's likely happening and how to fix it, in a way that 
builds genuine understanding rather than just naming the problem.

## Constraints
- Use an analogy suitable for a beginner
- Suggest at least 2 concrete techniques to address the issue
- Keep the tone encouraging, not critical

## Output Format
Respond using Markdown with these sections:
### What's Happening
### An Analogy
### How to Fix It"

Expected Output:
A well-structured Markdown response with three headers exactly as 
specified: "### What's Happening" correctly diagnosing overfitting 
(near-perfect training accuracy with much lower test accuracy is a 
textbook signature), "### An Analogy" offering a beginner-friendly 
comparison (e.g., memorizing exam answers versus actually 
understanding the material), and "### How to Fix It" suggesting at 
least two concrete techniques (e.g., regularization, dropout, early 
stopping, more training data, or data augmentation) — all delivered 
in an encouraging tone, correctly following both the requested 
structure and constraints.
