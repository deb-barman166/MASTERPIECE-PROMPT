-----------------------------
1. TITLE
-----------------------------
Prompt Optimization — Systematically Improving Prompt Performance

-----------------------------
2. DEFINITION
-----------------------------
Prompt Optimization is the systematic, often ITERATIVE and 
DATA-DRIVEN process of improving a prompt's performance against 
measurable criteria — accuracy, consistency, cost (token usage), 
latency, or task-specific quality metrics — through structured testing 
and refinement, rather than one-off intuitive tweaking. While Meta 
Prompting (file 67) covers using an LLM to help DESIGN or DIAGNOSE a 
prompt in a single pass, Prompt Optimization is the broader, more 
rigorous DISCIPLINE of treating prompt improvement as an ongoing, 
measurable process — testing variations systematically, tracking 
results, and converging on a genuinely better-performing version 
through evidence rather than guesswork.

Think of it like the difference between a marketer making one 
intuitive guess at improving an ad's headline (a single Meta Prompting-
style suggestion) versus running a proper A/B testing program that 
systematically tests multiple headline variations against real 
performance data, measures results rigorously, and converges on the 
genuinely best-performing option through evidence rather than 
intuition alone.

-----------------------------
3. PURPOSE
-----------------------------
Prompt Optimization exists to:
- Achieve MEASURABLE, VERIFIED improvement in prompt performance, 
  rather than relying on intuition or a single untested suggestion.
- Support PRODUCTION systems where prompt performance directly affects 
  real business/user outcomes, justifying systematic investment in 
  optimization.
- Balance MULTIPLE competing objectives (accuracy vs. cost vs. latency) 
  that a single "make it better" pass might not adequately account for.
- Provide a REPEATABLE PROCESS for prompt improvement that can be 
  applied to any prompt in a library, not just ad-hoc one-off fixes.
- Serve as the conceptual foundation for even more automated approaches 
  (Automatic Prompt Engineering, DSPy-Style Prompting) that formalize 
  and scale this same systematic optimization discipline using code and 
  algorithms rather than manual testing.

-----------------------------
4. WHEN TO USE AND BEST MODEL OR LLM
-----------------------------
WHEN TO USE:
- Production prompts used at meaningful scale/frequency, where 
  incremental performance improvements compound significantly over many 
  uses.
- Prompts with MEASURABLE success criteria (accuracy against a labeled 
  dataset, consistent format compliance, cost per query) that can 
  actually be tracked and compared.
- Situations with competing objectives requiring explicit trade-off 
  management (e.g., a more accurate but much more expensive prompt 
  variant vs. a cheaper but slightly less accurate one).
- Any prompt that's important enough to justify the additional time 
  investment of systematic testing beyond a single design pass.

WHEN NOT TO USE:
- One-off, low-stakes prompts where systematic optimization effort 
  exceeds the value of marginal improvement.
- Situations without any practical way to measure/compare prompt 
  performance objectively (in this case, focus on qualitative Meta 
  Prompting refinement instead).
- Very early-stage exploration where you're still discovering the basic 
  right approach, before optimization of a specific approach makes 
  sense.

BEST MODELS/TOOLS FOR PROMPT OPTIMIZATION:
- The optimization PROCESS itself is model-agnostic — you can optimize 
  prompts for Claude, GPT-4o/4.1/5-class, Gemini, or any other model, 
  since this is fundamentally about YOUR testing methodology, not a 
  specific model feature.
- Platforms with built-in EVALUATION/testing infrastructure (Anthropic's 
  Console prompt evaluation features, OpenAI's Evals framework, 
  various third-party prompt management platforms) provide 
  infrastructure specifically designed to support this systematic 
  testing process.
- For MORE AUTOMATED optimization, tools/frameworks like DSPy (covered 
  in file 79) can algorithmically search for improved prompts based on 
  defined metrics, representing a more automated evolution of the same 
  underlying discipline.
- Claude/GPT/Gemini can all serve as META-ANALYSIS assistants within 
  your optimization process — helping generate variant prompts to test, 
  or analyzing patterns in failure cases across your test set.

-----------------------------
5. PROMPT FORMULA
-----------------------------
    [DEFINE SUCCESS METRIC] + [ESTABLISH BASELINE PROMPT PERFORMANCE] 
    + [GENERATE VARIANT(S)] + [TEST VARIANTS AGAINST SAME METRIC/
    DATASET] + [SELECT BEST-PERFORMING VERSION] + [ITERATE]

-----------------------------
6. PROMPT STRUCTURE (as a process, not a single prompt)
-----------------------------
    1. Define Success Metrics — what specifically counts as "better" 
       (accuracy rate against known correct answers, consistency of 
       format compliance, average cost per query, human-rated quality 
       score).
    2. Establish a Test Set — a representative set of inputs (ideally 
       with known correct/expected outputs) to evaluate prompt 
       performance against consistently.
    3. Baseline Measurement — run your CURRENT prompt against the test 
       set and record its performance on your defined metrics.
    4. Generate Variants — create one or more alternative prompt 
       versions (potentially using Meta Prompting for variant 
       generation) hypothesized to improve on the baseline.
    5. Test Variants — run each variant against the SAME test set, 
       recording performance on the same metrics for fair comparison.
    6. Compare and Select — identify which version performs best 
       against your defined success criteria, accounting for any 
       trade-offs between competing metrics.
    7. Iterate — repeat the process, using the new best-performing 
       version as your updated baseline for further optimization 
       rounds.

-----------------------------
7. BEST PRACTICES
-----------------------------
- Define SUCCESS METRICS explicitly and objectively BEFORE testing 
  variants — deciding what "better" means after seeing results risks 
  unconsciously favoring whichever output you already like.
- Use a CONSISTENT TEST SET across all variant comparisons — comparing 
  different prompts against different inputs makes results 
  meaningless; fair comparison requires identical test conditions.
- Test MULTIPLE VARIANTS when possible rather than just one alternative 
  — this provides more information about which specific changes 
  actually drove any observed improvement.
- Account for COMPETING OBJECTIVES explicitly (a prompt that's 5% more 
  accurate but costs 3x more tokens may or may not be a genuine 
  improvement depending on your actual priorities) rather than 
  optimizing for a single metric in isolation.
- For SUBJECTIVE quality metrics (tone, creativity, style), consider 
  using human evaluation or a well-calibrated Evaluation Prompting 
  (file 65) setup rather than purely automated metrics that might miss 
  important qualitative factors.
- Keep a RECORD of what was tried and what results it produced — this 
  prevents redundant re-testing of previously-rejected approaches and 
  builds a knowledge base for future optimization efforts.
- Recognize DIMINISHING RETURNS — at some point, further optimization 
  effort yields smaller and smaller gains; know when a prompt is "good 
  enough" for your actual use case rather than optimizing indefinitely.

-----------------------------
8. COMMON MISTAKES
-----------------------------
- MISTAKE: Not defining success metrics objectively before testing, 
  leading to biased or inconsistent judgment about which variant is 
  actually "better."
  FIX: Define explicit, objective success criteria before beginning 
  variant testing.

- MISTAKE: Testing different variants against different inputs, making 
  comparison results meaningless.
  FIX: Always use the same consistent test set across all variant 
  comparisons.

- MISTAKE: Optimizing for a single metric (like accuracy) while 
  ignoring competing considerations (cost, latency), potentially 
  producing an impractically expensive "improvement."
  FIX: Explicitly account for all relevant competing objectives, not 
  just one metric in isolation.

- MISTAKE: Not keeping records of prior optimization attempts, leading 
  to redundant re-testing of previously-rejected approaches.
  FIX: Maintain a record of tested variants and their results.

- MISTAKE: Optimizing indefinitely without recognizing diminishing 
  returns, wasting effort on marginal gains that don't meaningfully 
  matter for the actual use case.
  FIX: Recognize when a prompt has reached "good enough" performance 
  for its practical purpose.

9. EXAMPLES (BASIC, INTERMEDIATE, ADVANCED)
-----------------------------

--- BASIC EXAMPLE ---
Process:
"Success metric: percentage of correctly classified support tickets 
(measured against 50 manually-labeled example tickets). 

Baseline prompt: 'Classify this ticket as Billing, Technical, or 
General.' → tested against the 50-ticket set → 76% accuracy. 

Variant: 'Classify this ticket as Billing, Technical, or General. 
Billing = payment/subscription issues. Technical = bugs/crashes. 
General = anything else.' (added brief category definitions) → tested 
against the SAME 50-ticket set → 89% accuracy. 

Result: Variant selected as new baseline, given clear, measurable 
improvement (76% → 89%) on the identical test set."

Expected Output:
A clear before/after comparison demonstrating the value of adding 
brief category definitions, with the improvement being genuinely 
measurable and attributable to a specific, identified change.

--- INTERMEDIATE EXAMPLE ---
Process:
"Success metrics: (1) percentage of generated product descriptions 
meeting our 50-70 word length requirement, (2) average tokens used per 
generation (cost proxy). 

Baseline prompt: 'Write a product description for [product], 50-70 
words.' → tested on 20 sample products → 60% met length requirement 
(many ran long), average 145 tokens used. 

Variant A: same prompt + 'Count your words before finalizing and 
adjust if needed to fit the range.' → tested on same 20 products → 85% 
met length requirement, average 180 tokens used (extra self-checking 
step added some cost). 

Variant B: same prompt + a concrete example showing the exact target 
length → tested on same 20 products → 90% met length requirement, 
average 155 tokens used. 

Result: Variant B selected — better length compliance AND lower token 
cost than Variant A, demonstrating that providing a concrete example 
was a more efficient fix than adding a self-verification instruction 
in this specific case."

Expected Output:
A clear multi-variant comparison across 2 competing metrics (accuracy/
compliance AND cost), correctly identifying Variant B as the superior 
choice since it wins on BOTH dimensions, rather than accepting Variant 
A's accuracy improvement without noting its added cost trade-off.

--- ADVANCED EXAMPLE ---
Process:
"I'm optimizing a prompt used in a production RAG pipeline that answers 
technical questions based on retrieved documentation. 

Success metrics: (1) factual accuracy against a held-out set of 30 
questions with verified correct answers, (2) rate of appropriate 
'insufficient information' acknowledgment when the retrieved context 
genuinely doesn't contain the answer (measured against 10 questions 
deliberately designed to have no good answer in the provided context), 
(3) average response latency. 

Baseline prompt: [current production prompt] → 83% accuracy on the 30 
answerable questions, but only 40% appropriate 'insufficient info' 
acknowledgment on the 10 unanswerable questions (it was frequently 
hallucinating plausible-sounding but unsupported answers instead) — 
2.1s average latency. 

Variant A: added explicit instruction 'If the context doesn't contain 
a clear answer, explicitly say so rather than guessing' → 81% accuracy 
on answerable questions (slight dip, worth investigating why), 90% 
appropriate acknowledgment on unanswerable questions (major 
improvement), 2.3s latency. 

Variant B: same addition as Variant A, PLUS a one-shot example 
demonstrating the desired 'insufficient information' response format → 
85% accuracy on answerable questions (actually improved over baseline), 
95% appropriate acknowledgment, 2.6s latency (added tokens from the 
example increased latency somewhat). 

Analysis: Variant B is the clear overall winner — it improves BOTH 
accuracy and appropriate uncertainty acknowledgment compared to 
baseline, at a modest latency cost (2.1s → 2.6s) that's likely 
acceptable given the significant quality gains, especially the 
critical reduction in hallucinated answers on genuinely unanswerable 
questions (40% → 95% appropriate handling). Recommend adopting Variant 
B as new production baseline, while flagging the latency increase for 
monitoring if response time becomes a bottleneck at higher query 
volumes."

Expected Output:
A rigorous, multi-metric optimization analysis correctly weighing 
three competing dimensions (accuracy, appropriate uncertainty handling, 
latency), identifying that Variant B represents a genuine, worthwhile 
improvement despite a latency cost, with an honest, transparent 
trade-off discussion rather than declaring victory based on a single 
metric alone — demonstrating the kind of rigorous, evidence-based 
decision-making that distinguishes systematic Prompt Optimization from 
ad-hoc tweaking.

-----------------------------
10. REUSABLE PROMPT TEMPLATE (as an optimization process checklist)
-----------------------------
    1. Define success metrics: [SPECIFIC, MEASURABLE CRITERIA — 
    accuracy, cost, latency, format compliance]
    
    2. Establish a consistent test set: [N REPRESENTATIVE INPUTS, 
    ideally with known/expected correct outputs]
    
    3. Baseline: Test [CURRENT PROMPT] against the test set. Record 
    performance on each defined metric.
    
    4. Generate variant(s): [ALTERNATIVE PROMPT VERSION(S)], each 
    hypothesized to improve on a specific weakness of the baseline.
    
    5. Test each variant against the SAME test set. Record performance 
    on the same metrics.
    
    6. Compare results across all metrics (not just one), accounting 
    for trade-offs between competing objectives.
    
    7. Select the best-performing version as the new baseline, and 
    document the decision/reasoning for future reference.
    
    8. Iterate as needed, recognizing when diminishing returns signal 
    it's time to stop.
